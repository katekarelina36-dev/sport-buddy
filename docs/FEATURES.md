## Known gaps vs. the full spec (by design, for a first scaffold)

- ~~F5 profile editing~~ **Fixed**: `app/profile/edit.tsx` — photo, name, bio, and preferred activities are editable from one screen (`Edit profile` button on My Profile). Not yet done: per-section inline pencil-icon editing (one field at a time, optimistic) as the spec originally describes — this is a single edit screen instead. Level isn't editable here yet (see the per-sport-level item below).
- **F16 device registration** — the API endpoint (`POST /notifications/push-tokens`) exists; the mobile app doesn't yet request permission / call it (needs `expo-notifications` + real FCM/APNs credentials to be meaningful).
- **Recurring events** (F12) — `TrainingSession.recurrenceRule` is modeled and accepted by the API; the job that actually expands a recurrence into future `TrainingSession` rows isn't implemented yet.
- **Swipe-to-decide on F8** — explicitly called out as "nice-to-have, not MVP-blocking" in the spec; buttons only for now.
- **Report/Block** (F4 safety requirement) and its moderation queue — not modeled yet.
- **Geo radius filtering** (PostGIS queries) — schema has `locationLat/Lng` and the Postgres image includes the PostGIS extension, but the feed query doesn't yet do a radius filter; profile-level exact-location-hiding (privacy requirement) also isn't enforced at the API layer yet.
- **Per-sport skill level in onboarding (F1)** — `UserActivity.level` already exists in the schema (one level per activity per user), but the onboarding wizard only collects a single overall level applied to `UserProfile.level`, and `PATCH /profile/me`'s `preferredActivityIds` creates each `UserActivity` with a hardcoded default level rather than a per-sport choice. Needs: (1) onboarding UI change — after picking sports, show a level picker per selected sport instead of one global level step; (2) `PATCH /profile/me` request shape change from `preferredActivityIds: string[]` to something like `preferredActivities: { activityId, level }[]`; (3) same treatment wherever else a level is set (F5 edit, F4 display already reads per-activity `level` correctly since the schema supports it).

None of these block the core loop (onboarding → post → request → approve → chat → schedule → challenge → complete) from working end-to-end.

## F1/F3/F4 redesign (pixel spec: name/city/DOB onboarding, profile-discovery feed)

A detailed design spec replaced the original F1/F3/F4 flow with a different discovery model: instead of browsing user-created "Activity Posts," F3 now shows cards of *people* who have set availability for a sport, and F4 is their full profile (not a post). Implemented:

- **F1** is now 4 steps: Name+City → Date of Birth (16+ enforced) → Sports with an inline per-sport level + weekly availability picker → Photo. `UserProfile` gained `city`/`dateOfBirth`; the old single profile-wide `level` field is unused (kept in the schema, harmless) in favor of per-sport `UserActivity.level` (closes the earlier per-sport-level backlog item).
- **`UserAvailability`** gained an optional `activityId` — `null` rows are "general" availability (F5/F9/F12 still use these), non-null rows are per-sport (set during F1, read by F3/F4).
- **`ActivityRequest`** now supports two shapes: the legacy `{postId, slotId}` (F7's original Activity Post flow — still functional but has no UI entry point anymore since nothing creates an ActivityPost from the app) and a new direct `{targetUserId, activityId}` (F3/F4's "Send Activity Request" button, no post involved). F8's approve/reject/pending queue handles both.
- **Report/Block** (previously just a backlog line) is now implemented: `UserReport` and `UserBlock` tables, `POST /users/:id/report`, `POST /users/:id/block`; blocked users are excluded from `/users/discover` in both directions. There's no admin-side view of reports yet — they're just recorded.
- **Not implemented**: the filter sheet's distance slider is UI-only — `/users/discover` doesn't yet apply `distanceKm` (same PostGIS-radius gap noted above).

None of this blocks trying the new flow end-to-end (onboard with a sport+schedule → browse the feed → open a profile → send a request → F8 → chat).

## Security backlog: user-uploaded photos

Current state (`lib/media.ts`, `routes/profile.ts` POST `/me/photo`) is a dev-only scaffold and has real gaps before this could hold real users' photos:

- ~~No server-side content-type validation / no size cap~~ **Fixed**: `POST /profile/me/photo` now caps raw upload size (8MB) and pipes the upload through `sharp` — decode-validates it's really an image, resizes to a fixed 512×512 JPEG, and strips EXIF metadata in the process (EXIF can carry GPS coordinates from the original photo — a privacy leak independent of the app's own location features).
- **No access control on serving media** — `/media/*` is still a public static route; anyone with a `photoUrl` can view it without being authenticated or matched with that user. Needs at minimum an auth check (or signed/expiring URLs once this moves to S3/GCS, per the README's swap-out plan).
- **No deletion path** — no way for a user (or an account-deletion flow) to remove a previously uploaded photo from storage; needed for any real privacy/right-to-erasure compliance.
- **Local disk storage** — fine for this dev scaffold; production must move to the S3/GCS `MediaDriver` already stubbed in `lib/media.ts`, with private-by-default bucket ACLs.

None of this blocks continued MVP testing with fake/throwaway photos; it matters before any real user's photo touches this system.

## Bug fixes: Schedule Event + Activity Post (implemented)

- **FAB / manual "Create Activity" removed.** There was already no FAB and no create screen left after the Round 2 redesign; the one remaining piece of the old manual flow — the unreachable `app/post/[postId].tsx` detail screen and its `POST /activity-posts` manual-create endpoint — has now been deleted outright, since nothing links to either.
- **Activity Posts are now fully auto-generated.** Saving per-sport availability (`PUT /availability?activityId=`, used by F1 onboarding and F5's "Preferred Activities") upserts an `ActivityPost` for that (user, sport) pair: `status: "active"` while the user has at least one day set, `status: "inactive"` the moment they clear all days for that sport. `ActivityPost` gained `autoGenerated` (always `true` now) and `maxParticipants`.
- **"How many partners are you looking for?" stepper** added to `SportAvailabilityCard` (shared by onboarding step 3 and F5), below the day/time availability — a −/+ stepper (1-20, default 1) with the spec's helper copy ("You'll be matched 1:1" / "A group chat will be created when partners are found"). - **Group-size enforcement**: approving an activity request (`POST /activity-requests/:id/approve`) now counts the recipient's already-approved requests for that sport against their own `maxParticipants` and rejects with 409 "This activity is full" once the cap is hit. **Gap**: each approval still opens its own ordinary 1:1 chat with the organiser rather than one shared group chat — a true multi-person chat needs the `chat_participants` restructuring called out as its own line item in the (still-deferred) Communities doc, so it wasn't built here to avoid a half-finished group-chat model.

A new `PATCH /training/:id` endpoint backs "edit mode."
- **Chat sticky banner rebuilt** to match the spec: sport icon+name, formatted date/time, location if set, and a status pill ("Scheduled" / "Completed ✓"). Tapping a "Scheduled" banner re-opens the Schedule Event sheet pre-filled with its current values; a "Completed" banner is not tappable. The existing "Complete" action (F14) is kept as a small link inside the banner rather than replacing the tap-to-edit behavior the spec asks for.

## Bug fixes, rounds 3-5 consolidated (implemented)

This was a large combined spec (9 sections). **Schema change, action needed on every existing dev database:** `Chat.activityId` is gone (replaced by a `ChatSport` join table) and `Chat` gained a `@@unique([userAId, userBId])` constraint — any local DB that already has two chats between the same pair of users (very likely from testing multi-sport matches) will fail a plain `prisma db push`. Reset with `npx prisma db push --force-reset` then reseed, rather than pushing over existing chat rows.

- **Section 1 — one chat per user pair.** `Chat` no longer carries a single `activityId`; a new `ChatSport` model (`chatId`, `activityId`, `activityRequestId`) tracks every sport a pair has matched on. Approving a second request between the same two people now upserts a `ChatSport` row onto their existing chat instead of creating a second thread (`POST /activity-requests/:id/approve`, `GET /activity-requests/sent`). The chat header now lists all matched sports ("Tennis, Running") instead of one.
- **Section 2 — multiple Event banners.** The chat screen now renders one banner strip per currently-scheduled Event (not just one), each with independent "Edit" and "Complete ✓" (Complete only once `scheduledAt` has passed) buttons; the first two show directly, a "+ N more" row expands the rest inside a 160px-tall scrollable area.
- **Section 3 — sport selector for multi-sport chats.** Tapping "Schedule Event" on a chat with 2+ matched sports opens `SportSelectorSheet` first ("Which sport?"); a sport that already has a scheduled Event shows a greyed-out "Scheduled" pill and isn't tappable. With only one matched sport, the selector is skipped as before. Enforced server-side too (`POST /training` now 409s if the sport isn't one of the chat's `ChatSport`s, or already has a `status: "scheduled"` Event).
- **Section 4 — first event vs. subsequent events.** `TrainingSession.isFirstBetweenUsers` is set at creation time (true only if no training in this chat has ever reached `completed`, across any sport). The full "How did it go?" Q1/Q2 sheet is now shown only for that one Event; every later Event (even a different sport) uses a plain "Mark this session as completed?" confirm dialog — `POST /training/:id/complete-simple` — which completes immediately, increments both counters, and never closes the chat.
- **Section 5 — post-first-event system messages.** Both the Q1/Q2 path and the simple-confirm path now post a "[Sport] session completed · [Date]" system message; if the first Event resolves with both sides wanting to continue, a second message nudges "Ready for the next session? Tap Schedule Event to plan it." (the tappable "Case A" green banner already does the actual navigation — the message is supplementary, not a live deep link).
- **Section 6 — real safe-area insets.** The hardcoded `topInset` constant is gone from `theme.ts`; `app/_layout.tsx` now wraps the app in `SafeAreaProvider`, and every screen with a custom header or no native header (chat, user profile, Preferred Activities, Home/Chats/My Profile/onboarding/auth) reads `useSafeAreaInsets()` directly for its top and bottom padding, so layout adapts to the real status bar / punch-hole camera / gesture bar instead of one fixed number for every device.
- **Section 7 — pending-requests badge.** A badge on the "Pending requests" button on My Profile shows the live pending count (1-9 exact, "10+", "50+", hidden at 0), pushed in real time over the existing chat socket's new per-user room (`emitToUser` in `sockets/chat.ts`, `requests:count` event) whenever a request is created, approved, or rejected, with a 60s poll (`GET /activity-requests/pending/count`) as a fallback (`usePendingRequestsCount` hook). Not implemented: visually clearing the badge to 0 just from opening the Requests screen while unhandled requests remain — the badge always reflects the true pending count instead, which is a deliberate deviation to avoid showing a misleading "0" with real unactioned requests still in the list.
- **Section 8 — Edit Profile fixes.** 8.1: the standalone "Edit availability" entry point is removed from My Profile (availability is edited inline per-sport on Preferred Activities); `app/availability.tsx` now only serves the F9 waitlist-subscribe flow. 8.2: already fixed in the previous bug-fix batch (fixed footer Save button); now also uses `insets.bottom` instead of a hardcoded platform check.
- **Section 9 — Send Activity Request sheet fixes.** 9.1: the Send Request button is now a fixed footer outside the sheet's `ScrollView`. 9.2: the earliest available day (Monday-first) is now pre-selected on open, so its time range shows immediately without a tap. 9.3: every day picker in the app (`WeeklyAvailabilityWidget`, `FilterSheet`, `WeekStrip`; `SportAvailabilityCard` was already Mon-first) now renders Mon..Sun instead of Sun..Sat — the underlying `dayOfWeek` values are unchanged (still JS `Date.getDay()` convention, 0=Sun), only the on-screen order changed. 9.4: the feed's "Couldn't find a match?" footer now uses `insets.bottom` instead of a fixed padding.

## Communities (full build) + Profile redesign (implemented)

Built from three new spec docs (`Communities_Updated.md`, `Profile_Page_Updated.md`, `BugFixes_Round6.md`). - **Mobile screens**: `app/(tabs)/communities.tsx` (list, client-side name search, locked/unlocked Create button), `app/communities/create.tsx` (photo, name, sport — scoped to `GET /training/completed-sports`, description, invite people you've played with via `GET /users/played-with`), `app/communities/[communityId].tsx` (hero + Join/Manage action + Events/Members/Feed tabs switched by tap, not navigation), `app/communities/[communityId]/chat.tsx` (group chat, same bubble/avatar-grouping pattern as 1:1 chat, no Schedule Event footer, organiser/assistant can long-press to pin a message), `app/communities/[communityId]/edit.tsx` (organiser-only name/photo/description edit — sport can't be changed after creation).
- **Real-time community chat**: `sockets/chat.ts` gained `community:join`/`community:message` socket events and an `emitToCommunity` helper, mirroring the existing 1:1 `chat:join`/`chat:message` pattern with a per-community room (`community:${id}`) instead of a per-chat one.
- **Profile page redesign** (`app/(tabs)/profile.tsx`): a fixed User Card (photo with an edit-icon overlay, name, age · city, a completed-events pill, "Edit Profile" button) and a fixed Requests row (people icon, label, the existing received-only pending-count badge, chevron, navigates to `/requests`) sit above a two-tab area (Preferred Activities / Communities) that scrolls independently, each tab with its own empty state and CTA ("Edit" / "Explore Communities").

## Sport photos: Unsplash, downloaded once and stored in our own DB (not bundled, not fetched at runtime)

Per explicit instruction: sport photos come from Unsplash, but are downloaded **once** by a script and stored through the app's *own* media pipeline (the same `mediaDriver` used for profile/community photo uploads), not bundled as local `require()` assets and not fetched from Unsplash at request time. This means the Unsplash access key only ever needs to exist on a developer's machine for as long as it takes to run the script — it can be deleted afterward with zero runtime impact.

- **`Activity.iconUrl`** (already present in the schema, previously unused) now holds each sport's stored photo URL — no schema migration needed.
- **`apps/api/scripts/downloadSportImages.ts`** (new, run manually — not part of the server or seed script): queries every sport with at least one active `ActivityPost`, fetches one Unsplash photo per sport (curated search terms per sport, e.g. "tennis court", falling back to "`<name>` sport" for anything uncurated), pipes it through `mediaDriver.store()`, and writes the resulting URL onto `Activity.iconUrl`. Skips any sport that already has a photo unless `--force` is passed. Run with `UNSPLASH_ACCESS_KEY=xxxxx npm run download:sport-images --workspace apps/api`; `UNSPLASH_ACCESS_KEY` is documented in `.env.example` but is **not required** for the app to run day-to-day — only for this one-time (or occasional re-run) script.
- **Mobile**: replaced the colleague's local `require()`-based `ACTIVITY_IMAGES` map on the Explore Activities cards with `activity.iconUrl` (resolved to a full URL via a new `resolveMediaUrl()` helper in `api/client.ts`, mirroring how `Avatar.tsx` already resolves profile photos) — the 5 static jpg assets that shipped in that commit are now dead weight and were removed. The Communities List card and the Send Activity Request hero also switched to this same source; all three fall back to a `#003161 → #006A67` gradient tile when a sport has no photo yet.

## Fix: Explore Activities sport photos not visibly loading

Reported as "images not loading" (worked fine on Communities). The `iconUrl` lookup itself was correct — no `sportImages.js`/`getSportImage()` dictionary exists in this codebase, so a name-casing mismatch (the first hypothesis) wasn't possible; photos come straight off each `Activity` row already returned by `GET /activities`, same source Communities uses. The real bug was in `ActivityCard`'s own rendering: the photo was drawn at 20% opacity *and* topped with a gradient that started at a fully **opaque** `#FAFAFA`, not transparent — opaque-over-faint hid the photo almost completely, which reads exactly like "didn't load" even though the URL resolved fine. Fixed by drawing the photo at full opacity and starting its wash gradient transparent (matching the Communities card's own gradient, which is why that screen looked fine) and switching the label to light text with a shadow so it stays readable over an actual photo instead of over a pale wash.
